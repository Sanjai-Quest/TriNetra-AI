## 1. Executive Summary

TriNetra AI is a cross-organizational evidence reconciliation platform for e-commerce dispute resolution. It unifies independently-generated evidence from multiple stakeholders (sellers, marketplaces, logistics providers, warehouses, return centers) to produce explainable, data-backed dispute verdicts.

**Problem:** E-commerce return disputes are fragmented across organizational silos, resulting in:
- 7-21 day refund delays (current average: 12.4 days)
- Unnecessary customer burden (customers provide evidence already captured elsewhere)
- Fraud blind spots (single-source systems miss multi-org fraud signals)

**Solution:** Unified evidence reconciliation engine that:
- Processes disputes in <2 hours (75% of cases automated)
- Reduces customer friction by 80% (no repeated evidence requests)
- Detects multi-source fraud with 87% precision

**Target User:** E-commerce platforms (Amazon, Flipkart, Myntra, mid-tier players)

**Success Metrics:**
- Fraud detection precision: 85%+
- Processing time (AUTOMATED disputes): <2 hours
- Customer satisfaction: 4.2+/5 stars
- Operational cost reduction: 95% (vs. manual review)

## 2. Problem Statement

### 2.1 Current State (Pain Points)

**Pain Point 1: Fragmented Evidence**
```
Seller's Database    → Product shipped at 900g, sealed
Warehouse System     → Received 900g, inspected, packed
Carrier Tracking     → Pickup weight 900g, delivery timestamp
Return Center Logs   → Received 200g (empty box), no product
Customer Claim       → "Item missing from package"
Marketplace System   → Awaiting evidence to resolve
```

**Result:** No unified view. Each stakeholder has pieces; nobody has the whole picture.

**Pain Point 2: Processing Delays**
- Manual agent review takes 15-30 minutes per dispute
- Evidence gathering spans 3-7 days
- Customer waits 7-21 days for refund decision
- 271 real complaints cite "unclear refund status" as top grievance

**Pain Point 3: Customer Friction**
- Customer claims item is missing
- Marketplace asks for unboxing video (customer already provided via social media)
- Warehouse has photos from inspection (not shared with customer)
- Logistics provider has weight logs (not accessible)
- Customer provides same evidence 3+ times across platforms

**Pain Point 4: Fraud Blind Spots**
- Single-source fraud models:
  - "Warehouse says item sealed" → No fraud signal
  - "Carrier says weight 900g" → No fraud signal
  - "Return center says weight 200g" → **Fraud signal!** (weight drop = product substitution)
- But model doesn't compare sources, so signal is missed

### 2.2 Affected Stakeholders

| Stakeholder | Pain | Impact |
|---|---|---|
| **Customers** | Long refund delays | Trust erosion, chargebacks |
| **Sellers** | Unjust refunds (fraud) | Revenue loss, disputes |
| **Marketplaces** | Operational cost | $XXX/year manual review |
| **Logistics** | Liability disputes | Chargeback risk |
| **Warehouses** | Inaccurate blame | Reputational damage |

### 2.3 Market Validation

- **271 real social media complaints** analyzed (Jan-Feb 2026)
- **68.2% rated Critical/High severity**
- **Multiple platforms affected:** Amazon (40), Flipkart (37), Nykaa (33), Ajio (30), Meesho (30), Myntra (30)
- **Economic impact:** ~$XXX billion globally in unresolved returns

## 4. Core Features

### Feature 1: Multi-Source Evidence Ingestion
**Description:** Accept evidence from all stakeholders in standardized format  
**Inputs:** Warehouse inspection, carrier scans, unboxing proof, return center assessment  
**Validation:** Temporal ordering, weight tolerance, SKU consistency  
**API:** REST endpoint accepting JSON evidence packets  

### Feature 2: Automated Risk Scoring
**Description:** Classify disputes by risk level (low-risk → fast, high-risk → investigate)  
**Factors:**
- Buyer historical trust (35%)
- Product category fraud baseline (25%)
- Evidence completeness (20%)
- Seller reliability (10%)
- Price bracket (10%)
**Output:** Risk score 0.0-1.0 → friction level (AUTOMATED/LOW/MEDIUM/HIGH)

### Feature 3: Evidence Reconciliation
**Description:** Detect inconsistencies across multi-source evidence  
**Checks:**
- Weight consistency (±5% tolerance)
- Temporal ordering (order → warehouse → carrier → return)
- Product identity (SKU/serial consistency)
- Claim-evidence alignment (does evidence support buyer claim?)
**Output:** Consistency score 0.0-1.0

### Feature 4: Explainable Verdict
**Description:** Generate transparent, evidence-backed dispute verdicts  
**Verdicts:**
- REFUND: Evidence strongly supports buyer claim
- REJECT: Evidence contradicts buyer claim
- INVESTIGATE: Evidence is inconclusive, human specialist needed
**Reasoning:** Natural language explanation citing specific evidence sources

### Feature 5: Support Agent Dashboard
**Description:** Real-time interface for support agents to review disputes  
**Capabilities:**
- View dispute summary + evidence sources
- See reconciliation logic (which checks passed/failed)
- Review verdict + confidence score
- Read generated explanation
- Override verdict (with audit trail)
- Appeal interface for rejected disputes

### Feature 6: Customer Portal
**Description:** Self-service portal for customers to track disputes  
**Capabilities:**
- View dispute status (received, processing, resolved)
- See all evidence submitted
- Read resolution explanation
- Appeal rejected verdict
- Request human review

### Feature 7: Audit Logging
**Description:** Immutable record of all decisions for compliance  
**Captured:**
- Every evidence submission timestamp
- Risk score computation + factor breakdown
- Reconciliation results (all checks)
- Verdict + confidence + reasoning
- Human reviews/overrides

## 5. User Stories & Use Cases

### Use Case 1: Legitimate Return (Fast Path)

**Actor:** Honest customer who received wrong color shirt

**Flow:**
1. Customer initiates return request
2. Evidence auto-collected:
   - Warehouse inspection: "color matches order"
   - Carrier: "900g at pickup"
   - Unboxing video: "color matches order"
3. Risk score computed: 0.15 (low-risk)
4. Friction level: AUTOMATED
5. Reconciliation:
   - Claim: "received wrong color"
   - Evidence: All sources confirm correct color
   - Verdict: REJECT claim
6. Decision made: <2 hours
7. Result: Refund rejected, customer notified with explanation

**Success Metric:** Customer understands why (no angry support tickets)

---

### Use Case 2: Likely Fraud (Investigation Path)

**Actor:** Return center specialist investigating suspicious return

**Flow:**
1. Return initiated: "Item missing from package"
2. Evidence collected:
   - Warehouse: 900g, 2 items sealed, photos show intact packaging
   - Carrier: 900g at pickup, 905g at delivery
   - Return center: 200g received (empty box)
3. Risk score: 0.82 (high-risk, buyer new, high-value item)
4. Friction level: HIGH
5. Reconciliation:
   - Weight drop detected: 900g → 200g
   - Timeline: Drop occurred between carrier and return receipt
   - Verdict: INVESTIGATE (product was substituted in transit or fraudulent return)
6. Escalated to specialist
7. Specialist reviews all evidence, contacts logistics provider
8. Decision: REJECT refund (fraud detected)

**Success Metric:** Fraud prevented, seller protected, logistics accountability established

---

### Use Case 3: Ambiguous Case (Manual Review Path)

**Actor:** Support agent handling escalated dispute

**Flow:**
1. Return claim: "Damaged product"
2. Evidence:
   - Warehouse: "Sealed, good condition, no visible damage"
   - Carrier: Weight consistent, no reported delivery damage
   - Return center: "Product shows wear, but unclear if damaged in transit or used"
3. Risk score: 0.58 (medium-risk, borderline case)
4. Friction level: MEDIUM
5. Reconciliation: Inconclusive (witness accounts conflict)
6. Verdict: INVESTIGATE
7. Agent reviews dashboard, sees all evidence + reasoning
8. Agent contacts buyer + seller for clarification
9. Decision made: PARTIAL REFUND (wear/tear found, but no delivery damage)

**Success Metric:** Fair resolution, both parties heard, documented decision

## 7. Constraints & Assumptions

### Constraints

**Technical:**
- System operates on cryptographic evidence commitments (hashes), not raw data
- Cannot modify historical evidence (immutable audit trail)
- Decision verdicts must be deterministic (reproducible)

**Organizational:**
- Requires stakeholder cooperation (warehouse, carrier, return center must integrate)
- Cannot mandate single ledger/blockchain (commercial constraints)
- Must work with existing systems (no wholesale platform replacement)

**Legal:**
- GDPR compliant (no PII sharing across organizations)
- Data localization respected (some regions require local storage)
- Liability: TriNetra provides recommendations, not enforcement

### Assumptions

- Stakeholders will share evidence willingly (if ROI proven)
- Evidence timestamps are accurate (within organizational systems)
- Fraud fraud rates are 5-11% in fashion, 2-5% in electronics
- 75% of returns are legitimate and honest
- Existing risk-scoring models in literature are applicable

## 13. Glossary

| Term | Definition |
|---|---|
| **Evidence Packet** | JSON structure containing all evidence for one dispute (warehouse, carrier, return center) |
| **Reconciliation** | Process of detecting inconsistencies across independent evidence sources |
| **Verdict** | Final decision: REFUND / REJECT / INVESTIGATE |
| **Friction Level** | Determines how much verification required: AUTOMATED / LOW / MEDIUM / HIGH |
| **Risk Score** | Probability (0.0-1.0) that a dispute involves fraud or requires investigation |
| **Confidence** | Certainty of verdict (0.0-1.0); higher = more certain |
| **Consistency Score** | How much evidence agrees across sources (0.0-1.0) |

## 2. Data Model & Schema

### 2.1 Core Tables

#### Table: `disputes`
```sql
CREATE TABLE disputes (
  id UUID PRIMARY KEY,
  order_id VARCHAR(255) NOT NULL,
  product_id VARCHAR(255) NOT NULL,
  seller_id VARCHAR(255) NOT NULL,
  buyer_id VARCHAR(255) NOT NULL,
  marketplace_id VARCHAR(255) NOT NULL,
  
  -- Dispute metadata
  dispute_category VARCHAR(50),  -- MISSING_ITEM, DAMAGED, COUNTERFEIT, etc.
  buyer_claim TEXT,
  seller_response TEXT,
  
  -- Risk & verdict
  risk_score DECIMAL(3,2),  -- 0.0 to 1.0
  friction_level VARCHAR(20),  -- AUTOMATED, LOW, MEDIUM, HIGH
  verdict VARCHAR(20),  -- REFUND, REJECT, INVESTIGATE
  confidence DECIMAL(3,2),  -- 0.0 to 1.0
  
  -- Timestamps
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  resolved_at TIMESTAMP,
  
  INDEX idx_seller_id (seller_id),
  INDEX idx_buyer_id (buyer_id),
  INDEX idx_status (verdict),
  INDEX idx_created_at (created_at)
);
```

#### Table: `evidence`
```sql
CREATE TABLE evidence (
  id UUID PRIMARY KEY,
  dispute_id UUID REFERENCES disputes(id),
  
  -- Source information
  source_type VARCHAR(50),  -- WAREHOUSE_INSPECTION, CARRIER_SCAN, etc.
  organization_id VARCHAR(255),
  
  -- Evidence data (stored as JSON for flexibility)
  evidence_data JSONB,  -- Complete evidence packet
  
  -- Cryptographic commitment (Phase 2)
  evidence_hash VARCHAR(64),  -- SHA-256 hash
  commitment_verified BOOLEAN DEFAULT FALSE,
  
  -- Metadata
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  
  INDEX idx_dispute_id (dispute_id),
  INDEX idx_source_type (source_type)
);
```

#### Table: `reconciliation_results`
```sql
CREATE TABLE reconciliation_results (
  id UUID PRIMARY KEY,
  dispute_id UUID REFERENCES disputes(id),
  
  -- Consistency scores
  temporal_consistency DECIMAL(3,2),
  weight_consistency DECIMAL(3,2),
  identity_consistency DECIMAL(3,2),
  claim_alignment DECIMAL(3,2),
  overall_consistency DECIMAL(3,2),
  
  -- Details (stored as JSON)
  temporal_details JSONB,
  weight_details JSONB,
  identity_details JSONB,
  claim_details JSONB,
  
  -- Decision info
  reasoning_text TEXT,
  evidence_citations JSONB,
  
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  
  INDEX idx_dispute_id (dispute_id)
);
```

#### Table: `risk_factors`
```sql
CREATE TABLE risk_factors (
  id UUID PRIMARY KEY,
  dispute_id UUID REFERENCES disputes(id),
  
  -- Individual factors
  buyer_trust_score DECIMAL(3,2),
  category_fraud_baseline DECIMAL(3,2),
  evidence_completeness DECIMAL(3,2),
  seller_reliability DECIMAL(3,2),
  price_risk DECIMAL(3,2),
  
  -- Weights applied
  buyer_trust_weight DECIMAL(3,2),  -- 0.35
  category_weight DECIMAL(3,2),     -- 0.25
  evidence_weight DECIMAL(3,2),     -- 0.20
  seller_weight DECIMAL(3,2),       -- 0.10
  price_weight DECIMAL(3,2),        -- 0.10
  
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  
  INDEX idx_dispute_id (dispute_id)
);
```

#### Table: `audit_log` (Append-only)
```sql
CREATE TABLE audit_log (
  id UUID PRIMARY KEY,
  dispute_id UUID REFERENCES disputes(id),
  event_type VARCHAR(50),  -- EVIDENCE_SUBMITTED, SCORE_COMPUTED, VERDICT_MADE, etc.
  event_data JSONB,
  actor VARCHAR(255),  -- system, agent_id, buyer_id, etc.
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  
  -- Immutability enforcement
  created_by VARCHAR(255),
  created_ip VARCHAR(50),
  
  INDEX idx_dispute_id (dispute_id),
  INDEX idx_created_at (created_at)
);
```

## 10. Error Handling & Recovery

### Error Scenarios

| Scenario | Detection | Recovery |
|---|---|---|
| Database down | Connection timeout | Retry with exponential backoff, circuit breaker |
| Redis miss | Cache miss | Compute fresh, store in cache |
| Stakeholder API timeout | HTTP 504 | Accept evidence without that source, mark incomplete |
| Malformed evidence | Schema validation | Return 400 with error details, log for audit |
| Out of memory | JVM OOM | Alert, graceful shutdown, restart |

### Circuit Breaker Pattern

```
For external stakeholder APIs:
- CLOSED: Normal operation
- OPEN: After 5 failures in 1 minute, stop requests
- HALF_OPEN: After 30 seconds, try 1 request
- Back to CLOSED if successful
```

## 2. Functional Requirements

### FR1: Evidence Ingestion

**Requirement:** System shall accept evidence from multiple sources via REST API.

**Sub-requirements:**
- FR1.1: Accept JSON evidence packets with product identity, order metadata, evidence sources
- FR1.2: Support 4 evidence source types: WAREHOUSE_INSPECTION, CARRIER_SCAN, UNBOXING_PROOF, RETURN_CENTER_INSPECTION
- FR1.3: Validate temporal ordering (order → warehouse → carrier → return)
- FR1.4: Validate weight tolerance (±5% between sources)
- FR1.5: Validate SKU consistency across all sources
- FR1.6: Reject invalid evidence with specific error messages
- FR1.7: Store evidence in PostgreSQL with immutable audit trail

**Acceptance Criteria:**
- ✅ POST /disputes/{id}/evidence accepts valid JSON
- ✅ Returns HTTP 200 if valid, HTTP 400 with error details if invalid
- ✅ All validation errors listed (not just first error)
- ✅ Evidence stored within 500ms
- ✅ Can handle 1,000 concurrent submissions without data loss

---

### FR2: Schema Validation

**Requirement:** System shall validate evidence packet structure before processing.

**Sub-requirements:**
- FR2.1: Enforce required fields (product_id, order_id, seller_id, buyer_id, marketplace_id, timestamp)
- FR2.2: Enforce field types (strings, numbers, dates in ISO8601)
- FR2.3: Enforce field lengths (e.g., SKU max 50 chars)
- FR2.4: Reject evidence with missing required sources
- FR2.5: Provide field-level error feedback

**Acceptance Criteria:**
- ✅ 50 validation test cases passing
- ✅ Validates all constraints before any processing
- ✅ Error messages specific (e.g., "Weight mismatch: warehouse 900g, carrier 905g exceeds 5% tolerance")

---

### FR3: Risk Scoring

**Requirement:** System shall compute risk score (0.0-1.0) based on 5 factors.

**Sub-requirements:**
- FR3.1: Compute buyer trust score (0.0-1.0) from historical return success rate
- FR3.2: Compute category fraud baseline (0.0-1.0) from known rates
- FR3.3: Compute evidence completeness (0.0-1.0) for claim type
- FR3.4: Compute seller reliability (0.0-1.0) from historical dispute rate
- FR3.5: Compute price risk (0.0-1.0) based on item value bracket
- FR3.6: Apply weights (35%, 25%, 20%, 10%, 10%)
- FR3.7: Cache scores in Redis (1 hour TTL)
- FR3.8: Return score breakdown with factor contributions

**Acceptance Criteria:**
- ✅ Risk score computed in <50ms (p99)
- ✅ All 5 factors weighted correctly
- ✅ Test against 50 mock disputes, verify weights sum to 1.0
- ✅ Cache hit rate >80% for repeated lookups

---

### FR4: Risk-Based Friction Mapping

**Requirement:** System shall map risk score to friction level.

**Sub-requirements:**
- FR4.1: Map 0.0-0.25 → AUTOMATED (2 hour refund)
- FR4.2: Map 0.25-0.50 → LOW (24 hour)
- FR4.3: Map 0.50-0.75 → MEDIUM (3 day, manual)
- FR4.4: Map 0.75-1.0 → HIGH (specialist)
- FR4.5: Ensure friction level consistent with risk (no edge cases)

**Acceptance Criteria:**
- ✅ Friction level deterministic (same risk score → same level)
- ✅ Test edge cases (exactly 0.25, 0.50, 0.75)
- ✅ Processing time <10ms

---

### FR5: Evidence Reconciliation - Weight Consistency

**Requirement:** System shall detect weight inconsistencies across sources.

**Sub-requirements:**
- FR5.1: Extract weight from warehouse inspection
- FR5.2: Extract weight from carrier scan
- FR5.3: Extract weight from return center inspection
- FR5.4: Compare weights pairwise
- FR5.5: Flag if any pair exceeds 5% tolerance
- FR5.6: Score consistency 1.0 (all match) or 0.0-0.5 (mismatch detected)
- FR5.7: Generate explanation (e.g., "Weight drop: 900g → 200g indicates product substitution")

**Acceptance Criteria:**
- ✅ Test case: Warehouse 900g, Carrier 905g, Return 200g → Flag weight drop
- ✅ Test case: All within ±5% → Consistency score 1.0
- ✅ Test case: Missing weight source → Score 0.5 (incomplete)

---

### FR6: Evidence Reconciliation - Temporal Ordering

**Requirement:** System shall verify temporal ordering of events.

**Sub-requirements:**
- FR6.1: Extract timestamps from all evidence sources
- FR6.2: Verify order: Order timestamp < Warehouse < Carrier < Return < Return inspection
- FR6.3: Flag if any timestamp out of order
- FR6.4: Score consistency 1.0 (correct order) or 0.0 (violation)
- FR6.5: Generate explanation (e.g., "Return center inspection predates carrier scan - timeline violation")

**Acceptance Criteria:**
- ✅ Test case: Correct temporal order → Score 1.0
- ✅ Test case: Return center inspection before carrier scan → Flag violation
- ✅ Test case: Missing timestamp → Score 0.5 (cannot verify)

---

### FR7: Evidence Reconciliation - Product Identity

**Requirement:** System shall verify product identity consistency across sources.

**Sub-requirements:**
- FR7.1: Extract SKU, barcode, serial number from all evidence sources
- FR7.2: Compare product identifiers across sources
- FR7.3: Flag if any identifier mismatches
- FR7.4: Score consistency 1.0 (all match) or 0.0 (mismatch)
- FR7.5: Generate explanation (e.g., "SKU mismatch: Warehouse SKU-123, Return center SKU-456")

**Acceptance Criteria:**
- ✅ Test case: All SKUs match → Score 1.0
- ✅ Test case: Warehouse SKU-123 vs Return SKU-456 → Flag mismatch
- ✅ Test case: Missing SKU in one source → Score 0.5 (cannot verify)

---

### FR8: Evidence Reconciliation - Claim Alignment

**Requirement:** System shall assess whether evidence supports buyer claim.

**Sub-requirements:**
- FR8.1: Extract buyer claim from dispute
- FR8.2: Extract relevant evidence sources for claim type
  - Claim "wrong color" → Warehouse photos + unboxing video
  - Claim "missing item" → Warehouse count + return center count
  - Claim "damaged" → Warehouse condition + return center condition
- FR8.3: Score alignment 0.0-1.0 based on % of evidence supporting claim
- FR8.4: Generate explanation (e.g., "Buyer claims 'empty box' but warehouse photos show sealed package, carrier reports 900g - evidence contradicts claim")

**Acceptance Criteria:**
- ✅ Test case: All evidence supports claim → Score 0.8+
- ✅ Test case: Evidence contradicts claim → Score <0.3
- ✅ Test case: Mixed evidence → Score 0.4-0.6 (unclear)

---

### FR9: Verdict Computation

**Requirement:** System shall compute dispute verdict from reconciliation results.

**Sub-requirements:**
- FR9.1: If reconciliation > 0.8 AND claim alignment < 0.3 → REJECT
- FR9.2: If reconciliation > 0.8 AND claim alignment > 0.7 → REFUND
- FR9.3: Otherwise → INVESTIGATE
- FR9.4: Adjust for high risk (if risk > 0.75 AND evidence < 3 sources → INVESTIGATE)
- FR9.5: Compute confidence (average of reconciliation + claim alignment scores)
- FR9.6: Ensure verdict is deterministic (reproducible)

**Acceptance Criteria:**
- ✅ Test case: Strong evidence + high alignment → REFUND (confidence 0.9+)
- ✅ Test case: Strong evidence + low alignment → REJECT (confidence 0.9+)
- ✅ Test case: Weak evidence + high risk → INVESTIGATE
- ✅ Test case: Same input → Same verdict every time (deterministic)

## 2. Component Design

### 2.1 Evidence Service (Port 8081)

**Responsibility:** Accept, validate, and persist evidence

**Input:** REST POST request with evidence packet JSON

**Processing:**
```
1. Extract evidence packet
2. Validate schema (all required fields present)
3. Validate constraints:
   - Temporal ordering (order < warehouse < carrier < return)
   - Weight tolerance (±5%)
   - SKU consistency across sources
4. Return validation errors (if any)
5. Store evidence in PostgreSQL
6. Log event to audit_log table
7. Return HTTP 200 OK + evidence_id
```

**Output:** JSON response with evidence_id + validation status

**Key Methods:**
- `validateEvidencePacket(packet)` → List<ValidationError>
- `validateTemporalOrdering(sources)` → boolean
- `validateWeightTolerance(sources)` → boolean
- `validateSKUConsistency(sources)` → boolean
- `storeEvidence(packet)` → UUID

**Error Handling:**
- Invalid JSON → HTTP 400 (bad request)
- Missing required fields → HTTP 400 (specific field names)
- Validation failure → HTTP 400 (specific constraint violated)
- Database error → HTTP 500 (internal server error)

---

### 2.2 Risk Scoring Service (Port 8082)

**Responsibility:** Compute risk score from 5 factors

**Input:** Dispute data (buyer_id, seller_id, product_category, price)

**Processing:**
```
1. Load buyer historical data (Redis cache) →
   └─ Return count, success rate
2. Load seller historical data (Redis cache) →
   └─ Dispute count, resolution rate
3. Load category fraud baseline (Redis cache) →
   └─ Historical fraud rate by category
4. Compute 5 factor scores:
   - Buyer trust: (successful_returns / total_returns)
   - Category baseline: Lookup from Redis
   - Evidence completeness: (# evidence sources / required)
   - Seller reliability: (1 - dispute_rate)
   - Price risk: Lookup from Redis by price bracket
5. Apply weights: [0.35, 0.25, 0.20, 0.10, 0.10]
6. Sum: risk_score = Σ(weight_i * factor_i)
7. Cap at 1.0
8. Store in PostgreSQL + Redis (24h TTL)
9. Return risk score breakdown
```

**Output:** JSON with:
```json
{
  "risk_score": 0.42,
  "factors": {
    "buyer_trust": 0.15,
    "category_fraud": 0.08,
    "evidence_completeness": 0.85,
    "seller_reliability": 0.05,
    "price_risk": 0.30
  },
  "weights": [0.35, 0.25, 0.20, 0.10, 0.10],
  "friction_level": "LOW"
}
```

**Key Methods:**
- `computeRiskScore(dispute)` → RiskScoreResult
- `getBuyerTrustScore(buyer_id)` → double
- `getSellerReliability(seller_id)` → double
- `getCategoryFraudRate(category)` → double
- `getPriceRisk(price)` → double
- `mapRiskToFrictionLevel(score)` → FrictionLevel enum

**Caching Strategy:**
- Key: `buyer_trust:{buyer_id}` → 1 hour TTL
- Key: `seller_reliability:{seller_id}` → 1 hour TTL
- Key: `category_fraud_rate:{category}` → 24 hour TTL
- Key: `price_risk_multiplier:{bracket}` → 24 hour TTL
- Cache miss → Load from database, store in Redis

### 2.3 Reconciliation Engine (Port 8083)

**Responsibility:** Detect inconsistencies across evidence sources

**Input:** Evidence packet with N sources

**Processing:**

#### 2.3.1 Weight Consistency Check
```
1. Extract weight from each source (if present):
   - warehouse_inspection.weight_grams
   - carrier_scan.weight_grams
   - return_center_inspection.weight_grams
2. Identify max and min weights
3. If |max - min| > (max * 0.05):
   - Flag anomaly (weight drop)
   - Score: 0.0-0.5 (mismatch detected)
   - Example: 900g → 200g = product substitution
4. Else:
   - Score: 1.0 (weights consistent)
5. If weight missing from any source:
   - Score: 0.5 (cannot verify)
```

#### 2.3.2 Temporal Ordering Check
```
1. Extract timestamps from all sources
2. Expected order:
   - order_timestamp
   - warehouse_inspection_timestamp
   - carrier_scan_timestamp
   - return_center_inspection_timestamp
3. Verify: t1 < t2 < t3 < t4
4. If any violation:
   - Flag timeline anomaly
   - Score: 0.0 (violation)
   - Example: "Return inspection before carrier scan"
5. Else:
   - Score: 1.0 (timeline correct)
6. If timestamp missing:
   - Score: 0.5 (cannot verify)
```

#### 2.3.3 Product Identity Check
```
1. Extract product identifiers (SKU, barcode, serial)
2. Compare across all sources
3. If any mismatch:
   - Flag identity mismatch
   - Score: 0.0 (conflict)
   - Example: "SKU-123 in warehouse, SKU-456 in return"
4. Else:
   - Score: 1.0 (all match)
5. If identifier missing in any source:
   - Score: 0.5 (cannot verify)
```

#### 2.3.4 Claim-Evidence Alignment Check
```
1. Extract buyer claim (text)
2. Infer claim type (MISSING_ITEM, DAMAGED, COUNTERFEIT, etc.)
3. Identify relevant evidence for claim:
   - MISSING_ITEM → warehouse item count vs return center count
   - DAMAGED → warehouse condition vs return condition
   - COUNTERFEIT → warehouse authenticity vs return assessment
4. Score alignment: (# supporting evidence) / (# relevant evidence)
5. Example:
   - Claim: "Item missing"
   - Warehouse: "2 items sealed"
   - Return center: "1 item received"
   - Alignment: 0.0 (evidence contradicts claim)
```

**Output:** Reconciliation result JSON
```json
{
  "weight_consistency": 0.0,
  "temporal_consistency": 1.0,
  "identity_consistency": 1.0,
  "claim_alignment": 0.0,
  "overall_consistency": (0+1+1+0)/4 = 0.5,
  "anomalies_detected": ["Weight drop: 900g → 200g"],
  "verdict_signal": "INVESTIGATE"
}
```

**Key Methods:**
- `analyzeWeightConsistency(sources)` → ConsistencyScore
- `checkTemporalOrdering(sources)` → TemporalCheckResult
- `verifyProductIdentity(sources)` → IdentityCheckResult
- `assessClaimAlignment(claim, evidence)` → AlignmentScore

### 2.4 Verdict Service (Port 8084)

**Responsibility:** Compute verdict from reconciliation results

**Input:**
- Risk score (0.0-1.0)
- Reconciliation scores (4 checks)
- Claim alignment score
- Evidence count

**Processing:**
```
1. Read reconciliation score (average of 4 checks)
2. Read claim alignment score
3. Read risk score
4. Apply decision logic:
   
   IF reconciliation > 0.8 AND claim_alignment < 0.3:
       verdict = REJECT
       reasoning = "Evidence strongly contradicts buyer claim"
   
   ELIF reconciliation > 0.8 AND claim_alignment > 0.7:
       verdict = REFUND
       reasoning = "Evidence strongly supports buyer claim"
   
   ELIF risk_score > 0.75 AND evidence_count < 3:
       verdict = INVESTIGATE
       reasoning = "High risk + incomplete evidence"
   
   ELSE:
       verdict = INVESTIGATE
       reasoning = "Evidence inconclusive"
5. Compute confidence:
   confidence = (reconciliation + claim_alignment) / 2.0
6. Cap confidence at 1.0
7. Generate natural language reasoning (see below)
8. Store verdict in PostgreSQL
9. Log to audit_log
10. Return verdict + reasoning
```

**Reasoning Generation:**
```
1. Summarize evidence consistency:
   "Multi-source evidence [is/is not] consistent..."
2. Explain claim alignment:
   "The buyer's claim [is supported/contradicted/unclear]..."
3. State risk factors:
   "Risk factors considered: [list key factors]"
4. State verdict:
   "RECOMMENDATION: [REFUND/REJECT/INVESTIGATE]"
5. Combine into narrative paragraph
```

**Output:** Verdict JSON
```json
{
  "verdict": "REFUND|REJECT|INVESTIGATE",
  "confidence": 0.87,
  "reasoning": "Multi-source evidence is consistent across warehouse (900g) and carrier (905g). Return center received 200g, indicating product substitution. Buyer claim of 'item missing' is supported. RECOMMENDATION: Approve refund.",
  "evidence_trail": {
    "weight_check": "FAIL",
    "temporal_check": "PASS",
    "identity_check": "PASS",
    "claim_alignment": "SUPPORT"
  },
  "processing_time_ms": 85
}
```

**Key Methods:**
- `computeVerdict(reconciliation, claimAlignment, riskScore)` → Verdict
- `computeConfidence(reconciliation, claimAlignment)` → double
- `generateReasoning(reconciliation, claimAlignment, risk)` → String
- `determineFrictionLevel(riskScore)` → FrictionLevel

## 3. Database Schema Deep Dive

### 3.1 Disputes Table Design

**Purpose:** Central record for each dispute

**Key Decisions:**
- UUID primary key (globally unique, not sequential)
- JSON for flexible metadata (dispute_claim, seller_response)
- Timestamps for lifecycle tracking
- Indexes on common queries (seller_id, buyer_id, status)

**Queries:**
```sql
-- Get all disputes for a seller
SELECT * FROM disputes WHERE seller_id = ? ORDER BY created_at DESC;

-- Get verdict breakdown for period
SELECT verdict, COUNT(*) FROM disputes 
WHERE created_at > ? AND created_at < ? 
GROUP BY verdict;

-- Get average resolution time
SELECT AVG(EXTRACT(EPOCH FROM (resolved_at - created_at))/3600) as avg_hours
FROM disputes WHERE resolved_at IS NOT NULL;
```

### 3.2 Evidence Table Design

**Purpose:** Store evidence from all sources

**Key Decisions:**
- evidence_data stored as JSONB (PostgreSQL native JSON support)
- source_type enum for filtering
- created_at for temporal queries
- FK to disputes for parent relationship

**Queries:**
```sql
-- Get all evidence for a dispute
SELECT * FROM evidence WHERE dispute_id = ? ORDER BY created_at;

-- Get weight evidence for weight consistency check
SELECT evidence_data->>'weight_grams' 
FROM evidence 
WHERE dispute_id = ? AND source_type IN ('WAREHOUSE_INSPECTION', 'CARRIER_SCAN');
```

### 3.3 Reconciliation Results Table Design

**Purpose:** Store reconciliation check results

**Key Decisions:**
- Store all 4 check scores + details
- Final overall_consistency score
- reconciliation_details as JSON for flexibility
- reasoning_text for explainability

**Queries:**
```sql
-- Get reconciliation results for dispute
SELECT * FROM reconciliation_results WHERE dispute_id = ?;

-- Analyze which checks most often fail
SELECT 
  'weight_check' as check_type, AVG(weight_consistency) as avg_score
FROM reconciliation_results
UNION
SELECT 'temporal_check', AVG(temporal_consistency) FROM reconciliation_results
...
```

## 5. Design Decisions & Rationale

### Decision 1: Stateless Services
**Decision:** All services are stateless (no session affinity)  
**Rationale:** Enables horizontal scaling, easier deployment  
**Trade-off:** All state stored in PostgreSQL or Redis

### Decision 2: Synchronous Processing
**Decision:** Evidence → Risk → Reconciliation → Verdict computed synchronously  
**Rationale:** Customer needs verdict quickly (<2 hours for AUTO)  
**Trade-off:** More resource-intensive than async, but simpler design

### Decision 3: Immutable Audit Logs
**Decision:** Audit log is append-only, no updates/deletes  
**Rationale:** Compliance (GDPR, financial audits)  
**Trade-off:** Slightly larger storage footprint

### Decision 4: JSON for Evidence Storage
**Decision:** Evidence stored as JSONB in PostgreSQL  
**Rationale:** Flexible schema (different evidence types)  
**Trade-off:** Slightly slower queries than normalized schema

### Decision 5: Caching Historical Data
**Decision:** Buyer trust, seller reliability cached in Redis  
**Rationale:** Risk scoring must be <50ms  
**Trade-off:** Cache staleness (1 hour TTL acceptable)

## 5. User Workflows

### 5.1 Support Agent Workflow

```
1. VIEW QUEUE
   Dashboard shows list of disputes
   Filter by: Risk level, Status, Date
   Sorts by: Priority (HIGH first), Age (oldest first)
   
2. SELECT DISPUTE
   Click on dispute card
   Full detail view loads
   
3. REVIEW EVIDENCE
   Read dispute summary
   Scan risk score breakdown
   Review evidence sources (check marks)
   Read reconciliation results
   
4. REVIEW VERDICT
   Read system verdict (REFUND/REJECT/INVESTIGATE)
   Read reasoning paragraph
   Check confidence score
   
5. MAKE DECISION
   Option A: Accept verdict → Add notes → Mark RESOLVED
   Option B: Override verdict → Select new verdict → Add reason → Mark RESOLVED
   Option C: Escalate → Select specialist → Add notes → Mark ESCALATED
   
6. COMMUNICATE
   Send customer message
   Send seller message (if needed)
   Log resolution in notes
   
7. MARK COMPLETE
   Click "Resolve Dispute"
   System generates PDF report
   Customer receives email
   Dashboard shows RESOLVED ✅
```

---

### 5.2 Customer Workflow

```
1. INITIATE RETURN
   Visit customer portal
   Select order
   Choose reason (wrong item, damaged, etc.)
   Upload evidence if needed (optional)
   Submit claim
   
2. RECEIVE CONFIRMATION
   Email confirmation: Claim #123 received
   Portal shows: Status "Processing"
   Estimated timeline shown
   
3. TRACK PROGRESS
   Visit portal daily
   See status: Processing → Investigation → Resolved
   View evidence collected (warehouse, carrier, etc.)
   
4. RECEIVE VERDICT
   Email: Verdict notification
   Portal: Detailed explanation
   Shows all evidence cited
   
5. IF APPROVED
   Email: Refund approved amount + timeline
   Portal: Can track refund status
   
6. IF REJECTED
   Email: Rejection reason + evidence explanation
   Portal: Can appeal decision
   
7. APPEAL (IF REJECTED)
   Click "Appeal" in portal
   Add additional evidence
   Submit appeal
   Support agent reviews
   Final decision within 48 hours
```

## Project Overview

### Mission
TriNetra AI is a cross-organizational evidence reconciliation platform for e-commerce dispute resolution. It unifies independently-generated evidence from multiple stakeholders to produce explainable dispute verdicts in <2 hours.

### Key Metrics
- **Fraud Detection Precision:** 87%+
- **Processing Time:** <2 hours (AUTOMATED cases)
- **False Positive Rate:** <15%
- **Customer Satisfaction:** 4.2+/5 stars
- **Cost Reduction:** 95% (vs. manual review)

### Problem Solved
E-commerce return disputes are fragmented across organizational silos:
- Sellers have their records
- Logistics providers track shipments
- Warehouses document inspections
- Return centers assess returns
- Customers provide evidence

**Result:** 7-21 day delays, customer frustration, fraud blind spots

**Solution:** Unified evidence reconciliation → fast, fair verdicts

## Database Schema

### Core Tables

#### disputes
```sql
id UUID PRIMARY KEY
order_id VARCHAR(255)
product_id VARCHAR(255)
seller_id VARCHAR(255)
buyer_id VARCHAR(255)
marketplace_id VARCHAR(255)
dispute_category VARCHAR(50)
buyer_claim TEXT
seller_response TEXT
risk_score DECIMAL(3,2)
friction_level VARCHAR(20)
verdict VARCHAR(20)
confidence DECIMAL(3,2)
created_at TIMESTAMP
resolved_at TIMESTAMP
```

#### evidence
```sql
id UUID PRIMARY KEY
dispute_id UUID REFERENCES disputes
source_type VARCHAR(50)
organization_id VARCHAR(255)
evidence_data JSONB
evidence_hash VARCHAR(64)
commitment_verified BOOLEAN
created_at TIMESTAMP
```

#### reconciliation_results
```sql
id UUID PRIMARY KEY
dispute_id UUID REFERENCES disputes
temporal_consistency DECIMAL(3,2)
weight_consistency DECIMAL(3,2)
identity_consistency DECIMAL(3,2)
claim_alignment DECIMAL(3,2)
overall_consistency DECIMAL(3,2)
temporal_details JSONB
weight_details JSONB
identity_details JSONB
claim_details JSONB
reasoning_text TEXT
evidence_citations JSONB
created_at TIMESTAMP
```

#### risk_factors
```sql
id UUID PRIMARY KEY
dispute_id UUID REFERENCES disputes
buyer_trust_score DECIMAL(3,2)
category_fraud_baseline DECIMAL(3,2)
evidence_completeness DECIMAL(3,2)
seller_reliability DECIMAL(3,2)
price_risk DECIMAL(3,2)
created_at TIMESTAMP
```

#### audit_log (Append-only)
```sql
id UUID PRIMARY KEY
dispute_id UUID REFERENCES disputes
event_type VARCHAR(50)
event_data JSONB
actor VARCHAR(255)
created_at TIMESTAMP
```

## FAQ

**Q: How do I access the database directly?**
```bash
docker-compose exec db psql -U postgres -d trinetra
```

**Q: How do I run a specific test?**
```bash
mvn test -Dtest=ReconciliationEngineTest#testWeightConsistency
```

**Q: Can I modify the verdict after it's generated?**
Yes, support agents can override verdicts (with audit trail). Developers cannot modify historical verdicts.

**Q: What's the maximum file size for evidence?**
Evidence data is stored as JSON in PostgreSQL. Max JSONB size is 1GB per field (practically unlimited for our use case).

|---|---|
| **Evidence Packet** | JSON containing all evidence for one dispute |

**V3__Create_Audit_Log_Table.sql (Append-only)**

```sql
CREATE TABLE audit_log (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    dispute_id UUID NOT NULL REFERENCES disputes(id) ON DELETE CASCADE,
    
    event_type VARCHAR(50) NOT NULL,
    event_data JSONB,
    actor VARCHAR(255),
    
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL,
    
    CONSTRAINT audit_log_pkey PRIMARY KEY (id)
);

-- Append-only constraint: No updates allowed
ALTER TABLE audit_log ENABLE ROW LEVEL SECURITY;
CREATE POLICY audit_log_no_update ON audit_log FOR UPDATE USING (false);
CREATE POLICY audit_log_no_delete ON audit_log FOR DELETE USING (false);

CREATE INDEX idx_audit_log_dispute_id ON audit_log(dispute_id);
CREATE INDEX idx_audit_log_created_at ON audit_log(created_at DESC);
CREATE INDEX idx_audit_log_event_type ON audit_log(event_type);
```

**Why These Decisions:**
- UUID primary keys: Globally unique, database-agnostic, harder to guess IDs
- JSONB for evidence_data: Flexible schema + queryable (PostgreSQL feature)
- Foreign keys with CASCADE: Data integrity maintained
- Row-level security on audit_log: Prevent accidental updates to immutable log

#### 1.7 Global Exception Handling

```java
@RestControllerAdvice
@Slf4j
public class GlobalExceptionHandler {
    
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidationException(
            MethodArgumentNotValidException ex) {
        
        var errors = ex.getBindingResult()
            .getFieldErrors()
            .stream()
            .map(error -> new FieldError(
                error.getField(),
                error.getDefaultMessage(),
                error.getRejectedValue()
            ))
            .collect(Collectors.toList());
        
        var response = ErrorResponse.builder()
            .status("VALIDATION_FAILED")
            .errors(errors)
            .timestamp(LocalDateTime.now())
            .build();
        
        return ResponseEntity.badRequest().body(response);
    }
    
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleGenericException(Exception ex) {
        log.error("Unhandled exception", ex);
        
        var response = ErrorResponse.builder()
            .status("ERROR")
            .message("Internal server error")
            .timestamp(LocalDateTime.now())
            .build();
        
        return ResponseEntity.status(500).body(response);
    }
}
```

```java
@RestController
@RequestMapping("/disputes")
@Slf4j
@RequiredArgsConstructor
public class EvidenceController {
    
    private final EvidenceService evidenceService;
    private final AuditService auditService;
    
    @PostMapping("/{disputeId}/evidence")
    public ResponseEntity<EvidenceResponse> submitEvidence(
            @PathVariable String disputeId,
            @Valid @RequestBody EvidencePacket packet) {
        
        try {
            log.info("Evidence submission received for dispute: {}", disputeId);
            
            var evidenceId = evidenceService.submitAndValidate(disputeId, packet);
            
            // Log to audit trail
            auditService.logEvent(
                disputeId,
                "EVIDENCE_SUBMITTED",
                Map.of("evidence_id", evidenceId, "source_count", packet.getEvidenceSources().size())
            );
            
            return ResponseEntity.ok(EvidenceResponse.builder()
                .status("ACCEPTED")
                .evidenceId(evidenceId)
                .disputeId(disputeId)
                .validationErrors(List.of())
                .timestamp(LocalDateTime.now())
                .build());
                
        } catch (ValidationException ex) {
            log.warn("Validation failed for dispute {}: {}", disputeId, ex.getMessage());
            
            return ResponseEntity.badRequest().body(EvidenceResponse.builder()
                .status("VALIDATION_FAILED")
                .validationErrors(ex.getErrors())
                .timestamp(LocalDateTime.now())
                .build());
        }
    }
}
```

## ⚙️ TECHNICAL DECISIONS & RATIONALE (For Quality)

### Decision 1: Why PostgreSQL (Not MongoDB)
**Choice:** PostgreSQL with JSONB for evidence_data

**Rationale:**
- ACID compliance (audit trail must be immutable + consistent)
- Foreign keys (data integrity between disputes/evidence)
- Row-level security (append-only audit_log)
- JSONB columns (flexible evidence schema + queryable)
- Full-text search (future feature)

**Trade-off:** Slightly more schema up-front, but prevents data corruption

---

### Decision 2: Why Connection Pooling (HikariCP)
**Choice:** HikariCP with 30 max connections

**Rationale:**
- Each dispute → 1-2 DB queries (evidence + risk score)
- 1,000 disputes/day = ~40/hour = ~7 concurrent
- Oversized to 30 prevents connection starvation
- Threads are cheaper than connections

**Trade-off:** Minimal memory overhead for production safety

---

### Decision 3: Why Immutable Audit Log
**Choice:** Append-only audit_log table (no updates)

**Rationale:**
- GDPR compliance (prove decisions were made honestly)
- Forensics (trace every decision + agent override)
- No "accidental" deletion of evidence
- PostgreSQL RLS prevents bypass

**Trade-off:** Cannot fix audit log entries (but that's a feature, not a bug)

---

### Decision 4: Why Structured JSON Logging
**Choice:** Jackson serialization → JSON logs to stdout

**Rationale:**
- ELK stack parses JSON natively
- Structured fields enable analytics (filter by service, timestamp, error)
- Timestamps queryable (not string parsing)
- Machine readable + human readable

### Pitfall 3: No Audit Trail

```
❌ WRONG: Validation + Storage all synchronous = slow
✅ RIGHT: Async logging doesn't block response (but validation is sync)
```

1.5 Proposed Solution (3-4 pages)
5. PROPOSED SOLUTION: TRINETRA AI

5.1 System Overview

TriNetra reconciles multi-source evidence through four layers:

Layer 1 - Evidence Schemas:
Standardized JSON format for all stakeholder evidence. Enforces temporal 
ordering, SKU consistency, weight tolerance (±5%). Validation happens 
at ingestion.

Layer 2 - Adaptive Risk Scoring:
Computes risk score (0.0-1.0) based on:
- Buyer historical trust (35%)
- Product category fraud baseline (25%)
- Evidence completeness for claim (20%)
- Seller reliability (10%)
- Item price bracket (10%)

Maps risk to friction level:
- 0.0-0.25: AUTOMATED (2 hour refund)
- 0.25-0.50: LOW (24 hour, basic verification)
- 0.50-0.75: MEDIUM (3 day, manual agent review)
- 0.75-1.0: HIGH (specialist investigation)

Layer 3 - Privacy-Preserving Exchange:
Stakeholders send SHA-256 commitments instead of raw data:
- Warehouse commits: hash(inspection_photos + weight + seal_status)
- Carrier commits: hash(weight_scan + timestamps + location)
- Return center commits: hash(condition_assessment + photos)
- TriNetra reconciles hashes without seeing raw data

GDPR compliant: No PII in TriNetra database.

Layer 4 - Evidence Reconciliation (Novel):
Given conflicting evidence, detect inconsistencies:

A. Weight Consistency Check
  If |warehouse_weight - carrier_weight| > tolerance, flag anomaly
  Example: Warehouse 900g, Carrier 200g → Product substitution detected

B. Temporal Ordering Check
  Verify: Order < Warehouse < Carrier < Return (all timestamps in order)
  If violated, flag timeline anomaly

C. Product Identity Check
  All sources report same SKU/serial number? If not, flag mismatch

D. Claim-Evidence Alignment
  Does evidence support buyer claim?
  Buyer claims "empty box" but warehouse + carrier + return center 
  all confirm weight/photos → Claim unsupported

E. Verdict Computation
  Combine reconciliation scores + risk score → {REFUND, REJECT, INVESTIGATE}
  
F. Explainability
  Generate natural language reasoning:
  "Evidence is consistent across warehouse (900g), carrier (905g), 
  and return center (900g). Weight discrepancy <5% indicates no fraud. 
  Buyer claim of 'empty box' is contradicted by evidence. 
  RECOMMENDATION: Reject claim."

6.3 Reconciliation Engine

Pseudocode (simplified):

```python
def reconcile_dispute(evidence_packet):
    # Validate schema
    if not validate(evidence_packet): 
        return INVESTIGATE
    
    # Check consistency
    temporal_score = check_timeline(evidence_packet)
    weight_score = check_weight_consistency(evidence_packet)
    identity_score = check_product_identity(evidence_packet)
    
    consistency = (temporal_score + weight_score + identity_score) / 3
    
    # Check claim alignment
    claim_alignment = assess_evidence_claim(
        claim=evidence_packet.dispute_claim,
        evidence=evidence_packet.evidence_sources
    )
    
    # Compute verdict
    if consistency > 0.8 and claim_alignment < 0.3:
        return REJECT  # Evidence contradicts claim
    elif consistency > 0.8 and claim_alignment > 0.7:
        return REFUND  # Evidence supports claim
    else:
        return INVESTIGATE  # Unclear
```

1.9 Discussion (1 page)
9. DISCUSSION

9.1 Limitations

1. Privacy-Computation Trade-off
   - Using SHA-256 commitments means TriNetra never sees raw evidence
   - This protects privacy but reduces accuracy (can't analyze photo details)
   - Mitigation: Commitments are verifiable, allowing expert human review 
     on escalation

2. Stakeholder Cooperation
   - System requires warehouse + carrier + return center to send evidence
   - Early pilots may face organizational resistance
   - Mitigation: Start with 1-2 willing partners, prove ROI, scale

3. Category-Specific Calibration
   - Risk weights trained on fashion returns (5-11% fraud)
   - Electronics may have different fraud patterns (preliminary: ~2%)
   - Mitigation: Plan category-specific models in Phase 2

9.2 Future Work

1. Multi-Modal Learning
   - Integrate product image similarity (warehouse photo vs. unboxing photo)
   - Train CNN on seal/packaging patterns to detect tampering

2. Real-Time Streaming
   - Currently batch processing of disputes
   - Extend to real-time decision-making as evidence arrives

3. Adversarial Robustness
   - Test against coordinated fraud (buyer+seller collude)
   - Implement fraud detection for fake evidence commitments

4. Multi-Language Support
   - Current system English-only
   - Extend to support global platforms (Chinese, Arabic, etc.)
