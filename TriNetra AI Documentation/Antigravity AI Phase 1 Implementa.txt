# Evidence Taxonomy for Phase 1

## Evidence Sources (8 types)

### 1. ORDER
- What: Initial customer order data
- Fields: order_id, product_id, sku, size, color, quantity, timestamp
- Example: {"order_id": "ORD-001", "sku": "TS-204", "size": "XL"}

### 2. SELLER
- What: Seller's dispatch/fulfillment record
- Fields: seller_id, order_id, product_id, sku, size, color, quantity, weight, timestamp
- Example: {"seller_id": "SELLER-123", "sku": "TS-204", "weight": 500, "timestamp": "2026-08-23T10:00:00Z"}

### 3. WAREHOUSE
- What: Warehouse receiving and inspection
- Fields: warehouse_id, order_id, product_id, sku, size, color, quantity, weight, seal_status, timestamp
- Example: {"warehouse_id": "WH-001", "sku": "TS-204", "weight": 505, "seal_status": "intact"}

### 4. PACKAGING
- What: Packaging operation (optional in Phase 1)
- Fields: packaging_id, order_id, product_id, sku, weight_packaged, timestamp
- Example: {"packaging_id": "PKG-001", "weight_packaged": 510}

### 5. CARRIER
- What: Logistics provider (pickup, in-transit, delivery)
- Fields: carrier_id, order_id, tracking_id, weight, timestamp
- Example: {"carrier_id": "CARRIER-001", "weight": 505, "timestamp": "2026-08-23T12:00:00Z"}

### 6. DELIVERY
- What: Delivery confirmation
- Fields: delivery_id, order_id, delivered_status, timestamp
- Example: {"delivery_id": "DEL-001", "delivered_status": "delivered", "timestamp": "2026-08-23T14:00:00Z"}

### 7. RETURN
- What: Return center receipt and inspection
- Fields: return_id, order_id, product_id, sku, weight, condition, timestamp
- Example: {"return_id": "RET-001", "sku": "TS-204", "weight": 210, "condition": "damaged"}

### 8. MARKETPLACE
- What: Dispute/complaint data
- Fields: case_id, order_id, customer_claim, timestamp
- Example: {"case_id": "CASE-001", "customer_claim": "item missing from package"}

## Normalization Rules (MUST implement)

### SKU Normalization
Input: "TS-204", "TS204", "ts-204", "TS 204"
Output: "TS-204" (canonical)
Rule: Convert to uppercase, insert hyphen between letters and numbers

### Weight Normalization
Input: "500g", "0.5kg", "500 grams", "0.5 kilograms"
Output: 500 (integer, in grams)
Rule: Convert all to grams, return as integer

### Size Normalization
Input: "XL", "x-large", "extra large", "extra-large", "xl"
Output: "XL" (canonical)
Rule: Map all variations to canonical size format

### Color Normalization
Input: "red", "RED", "dark red", "bright red"
Output: "RED" (canonical)
Rule: Convert to uppercase, remove modifiers for basic color

### Timestamp Normalization
Input: "2026-08-23T10:00:00Z", "08/23/2026 10:00 AM", "23-Aug-2026 10:00:00"
Output: "2026-08-23T10:00:00Z" (ISO 8601)
Rule: Convert all to ISO 8601 UTC format

## Conflict Types (5 types to test)

### 1. IDENTITY_CONFLICT
- Definition: Different sources claim different product IDs for same order
- Detection: Do all sources agree on SKU?
- Example: Seller says TS-204, Warehouse says TS-203
- Impact: HIGH (suggests wrong product dispatched)

### 2. SKU_CONFLICT
- Definition: Normalized SKUs don't match across sources
- Detection: Identity verification + SKU comparison
- Example: Order=TS-204, Warehouse=TS-203
- Impact: HIGH (variant mismatch)

### 3. WEIGHT_ANOMALY
- Definition: Weight drop > 3 standard deviations
- Detection: Statistical analysis (mean ± 3×stddev)
- Example: Outbound=500g, Return=210g (58% drop)
- Impact: MEDIUM-HIGH (suggests product missing)

### 4. TEMPORAL_CONFLICT
- Definition: Events out of chronological order
- Detection: Timestamp sequence validation
- Example: Warehouse timestamp BEFORE order timestamp
- Impact: MEDIUM (data quality issue)

### 5. MISSING_EVIDENCE
- Definition: Expected evidence source is absent
- Detection: Check for gaps in evidence chain
- Example: No carrier data between warehouse and return
- Impact: LOW-MEDIUM (incomplete picture)

### Identity Attributes
- product_id (UUID)
- order_id (UUID)

### Product Attributes

### Physical Attributes

- dimensions (string)

### Temporal Attributes
- timestamp (ISO 8601)
- event_type (string)

```markdown
# Conflict Taxonomy: Detection Rules & Output Format

## Conflict Detection Rules (MUST implement exactly)

### IDENTITY_CONFLICT Detection
```
IF (SELLER.sku ≠ ORDER.sku) OR (WAREHOUSE.sku ≠ ORDER.sku)
THEN
  OUTPUT: IDENTITY_CONFLICT
  SEVERITY: HIGH
  RECOMMENDATION: Verification required before dispatch
END
```

### SKU_CONFLICT Detection
```
same as IDENTITY_CONFLICT (in Phase 1, treat as same)
```

### WEIGHT_ANOMALY Detection
```
CALCULATE:
  mean_weight = average of all recorded weights
  stddev_weight = standard deviation
  threshold = mean_weight ± 3 * stddev_weight

FOR EACH evidence.weight:
  IF weight < (mean - 3*stddev) OR weight > (mean + 3*stddev)
  THEN
    OUTPUT: WEIGHT_ANOMALY
    SEVERITY: MEDIUM-HIGH
    ANOMALY_MAGNITUDE: (recorded_weight - expected_weight) / expected_weight
  END
END
```

### TEMPORAL_CONFLICT Detection
```
SORT all evidence by timestamp
FOR EACH adjacent pair (event1, event2):
  IF event1.timestamp > event2.timestamp
  AND event1.type should_precede event2.type
  THEN
    OUTPUT: TEMPORAL_CONFLICT
    SEVERITY: MEDIUM
    RECOMMENDATION: Check data quality
  END
END

Expected order:
1. ORDER
2. SELLER dispatch
3. WAREHOUSE receive
4. CARRIER pickup
5. DELIVERY
6. RETURN
```

### MISSING_EVIDENCE Detection
```
expected_sources = [ORDER, SELLER, WAREHOUSE, CARRIER, RETURN]
provided_sources = sources in this case

missing = expected_sources - provided_sources

IF len(missing) > 0
THEN
  OUTPUT: MISSING_EVIDENCE
  SEVERITY: LOW-MEDIUM
  MISSING: [list of sources]
  IMPACT: "Cannot fully reconcile without [missing sources]"
END
```

```markdown
# Phase 1 Evaluation Metrics

## Primary Success Metric: False Negative Reduction

```
FN_Reduction = (FN_Baseline - FN_TriNetra) / FN_Baseline * 100%

Where:
  FN_Baseline = False negative rate of best baseline (%) 
  FN_TriNetra = False negative rate of TriNetra (%)

Example:
  Baseline FN rate = 25%
  TriNetra FN rate = 15%
  FN_Reduction = (25-15)/25 * 100% = 40%

SUCCESS THRESHOLD: FN_Reduction > 15% with p-value < 0.05
```

## Secondary Metrics (MUST calculate all)

### Precision
```
Precision = TP / (TP + FP)

Where:
  TP = True Positives (correctly identified conflicts)
  FP = False Positives (incorrectly identified conflicts)

Interpretation: Of all conflicts flagged, how many are real?
Target: ≥0.80 (avoid falsely accusing innocent customers/sellers)
```

### Recall
```
Recall = TP / (TP + FN)

Where:
  TP = True Positives
  FN = False Negatives (missed conflicts)

Interpretation: Of all real conflicts, how many did we catch?
Target: ≥0.75 (catch 75%+ of actual issues)
```

### F1 Score
```
F1 = 2 * (Precision * Recall) / (Precision + Recall)

Interpretation: Balanced harmonic mean of precision and recall
Target: ≥0.77
```

### False Positive Rate (FPR)
```
FPR = FP / (FP + TN)

Where:
  FP = False Positives
  TN = True Negatives (correctly identified consistent cases)

Interpretation: Of all consistent cases, what % do we incorrectly flag?
Target: ≤0.15 (don't overwhelm reviewers with false alarms)
```

### False Negative Rate (FNR)
```
FNR = FN / (FN + TP)

Interpretation: Of all real conflicts, what % do we miss?
Target: <0.25 (TriNetra should catch at least 75% of real conflicts)
```

## Comparison Metrics (Must compare baseline vs. TriNetra)

### Per-Baseline Comparison

```
Baseline 1 (Identity-only):
  Precision_B1, Recall_B1, F1_B1, FPR_B1, FNR_B1

Baseline 2 (Weight-only):
  Precision_B2, Recall_B2, F1_B2, FPR_B2, FNR_B2

Baseline 3 (Timeline-only):
  Precision_B3, Recall_B3, F1_B3, FPR_B3, FNR_B3

TriNetra (Multi-source):
  Precision_T, Recall_T, F1_T, FPR_T, FNR_T

Comparison:
  Delta_Precision = Precision_T - max(Precision_B1, B2, B3)
  Delta_Recall = Recall_T - max(Recall_B1, B2, B3)
  Delta_F1 = F1_T - max(F1_B1, B2, B3)
  Delta_FNR = FNR_Best_Baseline - FNR_T  (FN reduction)
```

```

Test component importance by removing one at a time:

```

Report: p-value
Target: p-value < 0.05 (statistically significant improvement)
```

## Generation Rules (MUST follow)

1. **Use deterministic randomization** (seed-based, so results reproducible)
2. **Vary product attributes** (don't generate identical cases)
   - SKU: TS-204, TS-205, TS-206, etc.
   - Size: XL, L, M, S
   - Color: RED, BLUE, BLACK, WHITE
   - Base weight: 400-600g (varied)

3. **Add realistic noise** (±5g variance in normal cases)
   - Outbound weight: base_weight ± random(0-10)
   - Carrier weight: warehouse_weight ± random(0-10)
   - Return weight: outbound_weight ± random(0-10) for normal cases

4. **Timestamp progression** (events should flow forward)
   - Order: 2026-08-23T10:00:00Z
   - Seller: +15 min
   - Warehouse: +1 hour
   - Carrier: +2 hours
   - Return: +4 hours

5. **Never fake the ground truth** (trust your conflict injection)
   - If you injected a conflict, ground_truth = "CONFLICT"
   - If no conflict injected, ground_truth = "CONSISTENT"
   - Don't second-guess your own injection logic
